# Assignment 03 — MLOps AI Agent

An AI agent (Gemini tool calling) that answers questions about and operates an ML system built on
DVC, MLflow, Apache Airflow 3 and Kubernetes.

## Environment

- Python 3.12 via [uv](https://docs.astral.sh/uv/); dependencies pinned in `uv.lock`.
- Airflow 3.4 runs in its **own** venv (its constraint pins clash with MLflow); DAG tasks call the
  project venv's Python.
- Kubernetes: colima (k3s, docker runtime), so locally built images are visible to the cluster.
- Heavy local state lives outside the repo under `$DATA_ROOT` (on the dev machine an external SSD):

| Path under `$DATA_ROOT` | Contents |
|---|---|
| `venv/` | project venv (`.venv` is a symlink to it) |
| `venv-airflow/` | Airflow venv |
| `uv-cache/` | uv download cache |
| `dvc-cache/`, `dvc-remote/` | DVC cache and the default DVC remote `ssd` |
| `mlflow/`, `airflow/` | MLflow store, `AIRFLOW_HOME` |

### Setup

```bash
cp .env.example .env            # then fill in GEMINI_API_KEY etc.
set -a; source .env; set +a
mkdir -p $DATA_ROOT/venv && ln -sfn $DATA_ROOT/venv .venv
uv sync
uv venv --python 3.12 $DATA_ROOT/venv-airflow
VIRTUAL_ENV=$DATA_ROOT/venv-airflow uv pip install "apache-airflow==3.4.0" \
  --constraint https://raw.githubusercontent.com/apache/airflow/constraints-3.4.0/constraints-3.12.txt
.venv/bin/dvc cache dir --local $DATA_ROOT/dvc-cache
.venv/bin/dvc remote modify --local ssd url $DATA_ROOT/dvc-remote   # only if your path differs
.venv/bin/dvc pull
```

## Data (DVC)

`data/dataset.csv` is the sklearn breast-cancer dataset (binary `target`), generated by
`training/make_dataset.py`. Versions are git tags:

| Tag | Rows |
|---|---|
| `data-v1` | 400 |
| `data-v2` | 569 |

Reproduce an older version:

```bash
git checkout data-v1 -- data/dataset.csv.dvc && .venv/bin/dvc checkout
```

## MLflow + training

Start the tracking server (UI at http://127.0.0.1:5001; port 5000 is taken by macOS AirPlay):

```bash
scripts/start-mlflow.sh
```

`training/train.py` runs the pipeline as separate stages (the Airflow DAG calls each one):

| Stage | Does |
|---|---|
| `validate` | target present and binary, ≥100 rows, no nulls, all numeric |
| `preprocess` | dedupe, stratified 80/20 split |
| `train` | `StandardScaler` + `logreg` or `rf` |
| `evaluate` | accuracy/precision/recall/F1/ROC-AUC → MLflow run with provenance tags and the model |
| `gate` | F1 ≥ 0.95, ROC-AUC ≥ 0.97 and data matches DVC → register and set alias `@candidate`; otherwise fail and register nothing |

```bash
.venv/bin/python training/train.py all --model logreg --C 1.0
.venv/bin/python training/train.py all --model rf --n-estimators 200
```

Every run is tagged with `data_version` (the `data-*` git tag whose DVC md5 matches the file on disk),
`data_md5`, `data_matches_dvc`, `git_commit`, `git_dirty` and `quality_gate`. The registered model is
`breast-cancer-classifier`. Moving it from `@candidate` to production is a human decision.

## Airflow

```bash
scripts/start-airflow.sh   # UI + API on http://127.0.0.1:8080, user admin
```

On first start Airflow generates the admin password into
`$AIRFLOW_HOME/simple_auth_manager_passwords.json.generated`. Put it in `.env` as `AIRFLOW_PASSWORD`.

DAG `training_pipeline` (`dags/training_pipeline.py`), triggered on demand with params
`model` (`logreg`|`rf`), `C` and `n_estimators`:

```
validate_dataset → preprocess_data → train_model → evaluate_and_log_mlflow → quality_gate
```

- Each task runs one stage of `training/train.py` with the project venv. Every DAG run gets its own
  work folder `$DATA_ROOT/work/<run_id>`, and its MLflow run is tagged `pipeline=airflow:<run_id>`.
- Retries: 2 (15 s apart) for preprocess/train/evaluate. `validate_dataset` and `quality_gate` get 0,
  because a failed check would fail again.
- A failed `validate_dataset` or `quality_gate` stops everything after it, so no model is registered.

Trigger through the REST API (JWT auth):

```bash
TOKEN=$(curl -s -X POST localhost:8080/auth/token -H 'Content-Type: application/json' \
  -d "{\"username\":\"admin\",\"password\":\"$AIRFLOW_PASSWORD\"}" | jq -r .access_token)
curl -s -X POST localhost:8080/api/v2/dags/training_pipeline/dagRuns \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"logical_date": null, "conf": {"model": "rf", "n_estimators": 150}}'
```

**Injected failure (verified):** 30 missing values were written into `data/dataset.csv`.
`dvc status` reported the file modified, `validate_dataset` failed with
`dataset validation failed: 30 missing values`, and the 4 tasks after it ended `upstream_failed`.
No MLflow run or model version was created. Fixed with `dvc checkout --force data/dataset.csv`.

## Prediction service on Kubernetes

`serving/app.py` is a FastAPI service with `/health` (liveness), `/ready` (readiness: 503 with the
reason if the model failed to load), `/version` (model version + provenance) and `/predict`.
`serving/export_model.py` exports a registered version from MLflow, and the `Dockerfile` bakes it into
the image tagged `prediction-api:model-v<N>`, so the image tag says exactly which model is deployed.

```bash
scripts/deploy-k8s.sh            # deploy the @candidate model (or pass a version number, e.g. 8)
```

The script exports the model, builds the image in colima's Docker (visible to k3s, so no registry is
needed), updates the tag in `kubernetes/deployment.yaml` and runs `kubectl apply`.

Manifests in `kubernetes/` (namespace `mlops-app`):

| File | What |
|---|---|
| `deployment.yaml` | 2 replicas, rolling update with `maxUnavailable: 0`, readiness `/ready` + liveness `/health`, requests 100m/192Mi, limits 500m/512Mi, non-root |
| `service.yaml` | ClusterIP, port 80 → 8000 |
| `configmap.yaml` | `LOG_LEVEL`, `PREDICTION_THRESHOLD`, `MODEL_DIR` |

Try it:

```bash
kubectl get --raw /api/v1/namespaces/mlops-app/services/prediction-api:http/proxy/version
kubectl -n mlops-app port-forward svc/prediction-api 18080:80   # then POST localhost:18080/predict
```

**Injected failure (verified):** `kubectl set image ... api=prediction-api:model-v99` (the tag doesn't
exist). The new pod went `ErrImagePull` → `ImagePullBackOff`, and the Warning events said
`pull access denied for prediction-api`. Because `maxUnavailable: 0`, both v8 pods stayed Ready and
the service never went down; the rollout just stalled (`UP-TO-DATE 1`, `AVAILABLE 2`). Fixed with
`kubectl rollout undo deployment/prediction-api`.

## The agent

Gemini (`GEMINI_MODEL`, default `gemini-3.5-flash-lite`) with function calling over 28 tools in
`agent/tools/` (DVC, MLflow, Airflow, Kubernetes). It uses the Interactions API with `store=False`:
the conversation history is kept by the agent, and tool output is not stored by Google.

```bash
uvicorn api.main:app --port 8000          # HTTP API (needs GEMINI_API_KEY in .env)
python -m agent.main                      # terminal chat
python -m agent.main "Is the prediction API healthy?"
```

```bash
curl -s localhost:8000/chat -H 'Content-Type: application/json' \
  -d '{"message": "Find the best recent model, identify the dataset version used to train it, check the deployment status, and explain whether retraining is necessary."}'
```

The response has `answer`, `tool_calls` (each tool with its args, status and duration) and
`pending_actions`.

**Safety model**

- Every tool call goes through `agent/tools/base.py:run_tool`: argument validation, allowlist
  checks (namespace `mlops-app`, DAG `training_pipeline`, read-only dvc/git subcommands), timeout,
  error capture, and one JSON log line per call (request id, tool, status, duration, redacted args).
- `trigger_dag`, `restart_deployment` and `scale_deployment` never run on the model's say-so. The
  call becomes a pending action with an id. It runs only when the user sends that id back in
  `confirm_action_ids`, and it runs with exactly the arguments that were proposed.
- A failed, timed-out or denied tool is reported to the model as such, and the system prompt requires
  the answer to say what could not be verified. If the Gemini call itself fails, the API returns
  502 instead of an answer.
- Retraining is only recommended on evidence: a failed gate, a newer dataset version than the
  deployed model's, a model older than `MODEL_MAX_AGE_DAYS` (30), or degradation results the user
  supplied.

```bash
# 1. ask; the response lists a pending action, e.g. {"action_id": "71b2b9cc", "tool": "trigger_dag", ...}
curl -s localhost:8000/chat -H 'Content-Type: application/json' \
  -d '{"message": "Trigger the training pipeline with a random forest of 120 trees and report whether it succeeded."}'
# 2. confirm it in the same session
curl -s localhost:8000/chat -H 'Content-Type: application/json' \
  -d '{"message": "Confirmed.", "session_id": "<session_id>", "confirm_action_ids": ["71b2b9cc"]}'
```
